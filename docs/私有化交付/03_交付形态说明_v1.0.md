## 一、一句话交付形态

**在医院信息科机房里放一台服务器，我们的系统以 Docker 容器跑在上面；医生在诊室浏览器里打开一个院内网址就能用，问诊录音和病历数据全部留在医院内网，一个字都不出院。**

对应三个结构性选择，每个都直接对应医院的实际关切：

| 选择 | 做法 | 解决医院什么顾虑 |
|---|---|---|
| **私有化部署**（非 SaaS） | 系统部署在院内服务器，非乙方公网托管 | 患者数据不出院，等保与数据安全责任边界清晰 |
| **B/S 架构**（非客户端） | 医生用 Chrome/Edge 打开网页，零安装 | 与 HIS/EMR 使用习惯一致，信息科无需逐台装机、无升级分发负担 |
| **容器化交付**（非裸机安装） | 镜像离线包 + 一键脚本，版本可追溯 | 环境依赖自带，不受院内操作系统版本差异影响；升级回滚是换镜像而非改系统 |

## 二、交付边界：我们交什么、不交什么

专业系统交付最容易含糊的就是边界。先把边界划清：

### 2.1 乙方交付（交付包 `mra-delivery-v<版本>.tar.gz`）

| # | 交付物 | 说明 |
|---|---|---|
| 1 | **离线镜像包** `images/*.tar` | 预构建应用镜像（内含 ffmpeg 及可选本地语音识别依赖）、nginx 静态站镜像、可选 MySQL 镜像。院内 `docker load` 导入，**全程不需要外网** |
| 2 | **全量代码** `code/` | 前端工作台 / 后端 API / 语音识别 MCP 服务 / 运维工具，院内可选入 Git |
| 3 | **一键安装脚本** `install.sh` | 环境检查 → 导入镜像 → 文件落位 → 生成配置文件 → 启动 → 部署验证，**幂等**（重复执行安全，不覆盖已填配置） |
| 4 | **交付自检 / 验收脚本** `verify.sh` | 交付包完整性自检（含校验和）+ 部署后自动化验收，输出可直接贴入验收报告 |
| 5 | **配置模板** `llm_env.template` | 全部配置项字典与填写说明，**不含任何真实密钥** |
| 6 | **文档集** `docs/` | 部署说明书、验收报告模板、HIS 接口字典、录音知情同意书模板、HIS 对接需求函、字段确认表 |
| 7 | **运维脚本** `scripts/backup-db.sh` | 数据库备份与轮转（默认保留 14 份） |
| 8 | **本地模型** `models/`（可选） | 选择"全本地零外呼"方案时，语音识别模型随包离线带入 |
| 9 | **培训与验收** | 信息科运维培训 + 使用科室操作培训 + 双方签字的验收报告 |

整套包由仓库 `deploy/offline/make_delivery.sh` 一键生成，打包过程**强制两道红线**：代码经 rsync 排除患者资料/真实录音/密钥/数据库文件；产物再做二次扫描（音频文件、患者代号映射、疑似密钥零命中才放行），并生成全包 SHA256 校验清单。

### 2.2 院方提供（交付前置条件）

| # | 事项 | 对应文档 |
|---|---|---|
| 1 | 内网服务器（配置建议见 §四）与固定内网 IP | 说明书 §2.1 |
| 2 | MySQL 实例与独立库/账号（可复用院内现有实例） | 说明书 §5.4 |
| 3 | 院内 nginx 入口反代 + 内网 DNS 别名 + HTTPS 证书 | 说明书 §4.6、§2.4 |
| 4 | HIS 数据供给（8 张表导出或视图，字段字典已给到信息科） | `docs/HIS数据接口说明_8表字典_v1.0.md` |
| 5 | 录音知情同意流程落地（医务科审定同意书模板） | `docs/对院方推进/01_录音知情同意书模板` |
| 6 | 试点科室与账号名单（住院医师/上级医师/质控科三类角色） | `docs/对院方推进/03_字段地图v0_确认表` |

### 2.3 明确不在交付范围

说清"不做什么"比罗列"做什么"更能建立信任：

- **不做 HIS/EMR 的替代或侵入式改造**：本系统是并行辅助工具，通过只读数据供给获取素材，不接管医院既有的病历书写主流程。
- **不承诺 AI 全自动出病历**：系统生成的是**草稿**，必须经医生四色确认后才归档，责任主体始终是医生（见 §六）。
- **不做模型训练数据的对外输出**：院内数据留在院内；模型优化采用"院内脱敏语料回流 + 引擎/规则包分发"的方式（详见 `docs/自建ASR选型与实施路径.md`）。
- **不包含院方机房硬件、网络改造、等保测评执行**：测评由院方统筹，我方提供部署形态说明与配合材料。

## 三、系统在院内长什么样

```
医生 PC / 护士站 PC（Chrome / Edge）
        │  院内地址： https://mra.<医院域名>/mra/
        ▼
┌─ 院内服务器（信息科机房 · Docker）──────────────────┐
│                                                      │
│  ① 医生端网页工作台（nginx 静态容器）                 │
│     宿主端口 127.0.0.1:3904 → 工作台/审签/质控页面     │
│                                                      │
│  ② 应用 API 服务（Python 容器）                       │
│     宿主端口 127.0.0.1:3905 → 认证 / AI 生成 /         │
│     归档审签 / 录音转写（内部经 MCP 协议调用 ASR）      │
│                                                      │
│  ③ MySQL 8（复用院内实例，或随包容器化）               │
│     启动自动建表：用户 / 会话 / 归档 / 审计日志          │
│                                                      │
│  ④ 录音与转写文件（院内本地目录，随归档管理）           │
└──────────────────────────────────────────────────────┘
        │
        ▼ 仅两类对外依赖，二选一（见 §五）
   [方案A] 防火墙白名单 → LLM 云 API / 语音云 API
   [方案B] 全部本地 → 本地 LLM 服务 + 本地语音识别（零外呼）
```

两个要点：

1. **容器端口只绑 `127.0.0.1`**，所有外部访问必须经院内 nginx 统一入口——刻意如此，便于信息科统一管控、统一审计、统一 HTTPS。
2. **AI 能力只有两个对外依赖**：语言模型的生成服务、语音识别服务。这两个的取舍决定了整个交付方案的合规强度，是实施前必须与信息科确认的**唯一关键决策**（§五）。

## 四、环境要求（院方需准备的）

| 项 | 最低 | 建议 |
|---|---|---|
| CPU | 2 核 | 8 核+（若采用本地语音识别/本地大模型，需另配 GPU 服务器评估） |
| 内存 | 4 GB | 16 GB+ |
| 磁盘 | 40 GB | 200 GB+（病历文书 + 录音归档 + 数据库 + 备份轮转） |
| 操作系统 | Ubuntu Server 22.04/24.04（已验证）、麒麟 V10 等 Linux 发行版 | 同左 |
| Docker | 20.10+ 与 Compose v2 | 院内无外网时用我方提供的离线安装包 |
| 浏览器 | Chrome / Edge 最新版 | — |

> **两容器资源占用很低**（静态站限幅 96MB、API 限幅 512MB，实测内存远低于限幅）。磁盘主要由**录音文件**驱动，可按"每床日录音 2 分钟约 2MB"估算；正式上线前会与信息科一起按试点科室规模核算容量。

### 一个必须提前知道的浏览器硬约束（录音功能）

医生端用浏览器麦克风录音时，浏览器安全策略规定**只有 HTTPS 页面或本机 localhost 才能申请麦克风**。因此：

- 若只配 `http://192.168.x.x/mra/`，麦克风会被浏览器**直接禁用**；
- 正式交付必须二选一：
  - **推荐**：配内网 DNS 别名（如 `mra.hospital.local`）+ HTTPS 证书（院内 CA 签发，或自签证书导入工作站信任列表）→ 以 `https://` 访问，录音全功能可用；
  - **过渡期**：改用"录音笔/手机录音 → 上传音频文件"通道（文件上传不受此限制），病历生成能力完全不受影响。

这件事**必须在实施前就跟信息科对齐**，否则验收时"录音用不了"会变成扯皮项。我方在交付说明书中已把它列为硬约束并给出两种解法。

## 五、关键决策：网络与 AI 能力的三种方案

整个交付方案里**只有一个需要院方拍板的技术决策**——AI 能力从哪来。三种方案按合规强度递进：

| | 方案A：白名单 + 云端 API | 方案B：全本地零外呼 | （混合） |
|---|---|---|---|
| 形态 | 防火墙放行语言模型与语音识别的云 API 域名 | 本地 GPU 部署开源大模型 + 本地语音识别 | 试点期A、正式期切B |
| 患者数据流向 | **病历文本/录音会经 HTTPS 出医院**（需与厂商签署不留存条款） | **完全不出院** | 分阶段 |
| 识别/生成质量 | 最优（云端大模型 + 方言热词） | 中等（开源模型，方言准确率下降，需本地评测） | 先优后调 |
| 新增硬件 | 无 | 需 GPU 服务器 | — |
| 等保配合 | 需在委托处理/数据出境条款中说明 | 最简（物理隔离） | — |
| 适用 | 试点期快速上线 | 信息科要求严格 / 正式运行期 | **推荐路径** |

**关键工程事实：这三种方案对系统来说是纯配置差异，切换不动一行代码。** 语言模型只要兼容 OpenAI 接口，改配置地址即可；语音识别引擎在适配器契约下可插拔（云端厂商 / 本地开源引擎均已留位）。因此建议按"**试点期方案A（质量优先）→ 并行开展本地评测 → 按信息科要求切方案B**"推进，把合规选择权完整交给院方，而不是绑架院方的技术路线。

> 语音识别这一环，我方已有完整的自建路线与实测数据（本地引擎零外呼可跑、方言纠错级联、热词表、评测口径），见 `docs/自建ASR选型与实施路径.md`——这不是纸面方案，而是已经在真实录音上跑出过对比数据的。

## 六、合规与责任设计（这套系统凭什么能进医院）

医院上专业系统，技术之外更看**责任划分**。我方把这几条做进了系统本身，而不只是写进合同：

| # | 设计 | 说明 |
|---|---|---|
| 1 | **数据不出院** | 数据库、病历文书、录音全部落院内存储；方案B 零外呼，方案A 仅白名单域名可达（可抓包/查防火墙日志复核） |
| 2 | **四色确认（严禁臆造）** | 每个字段标来源：蓝=系统带入／绿=对话提炼（可溯源到录音原文）／灰=规范所见／黄=缺失待补。**无录音时病史类字段硬拦截，宁缺毋造** |
| 3 | **责任主体始终是医生** | AI 只出草稿；医生确认后归档，归档产生正式编号。系统不做、也无法做"自动归档" |
| 4 | **全程审计留痕** | 登录/生成/归档/审签/抽查/转写全部只追加写审计日志，质控科可在系统内按时间查阅，不可篡改 |
| 5 | **角色与权限** | 住院医师=书写确认／上级医师=签发退回／质控科=抽查+审计，越权请求被拒 |
| 6 | **口令与会话安全** | 口令 PBKDF2-HMAC-SHA256 20 万轮加盐哈希；登录防爆破（15 分钟内 5 次失败锁定 15 分钟）；会话 HttpOnly Cookie |
| 7 | **交付物零患者数据** | 代码与镜像只含脱敏演示数据（患者A–F），`tools/check_repo.py` 可现场复验红线（患者真名/电话/住址/院内ID 零入库） |
| 8 | **录音合规** | 问诊录音按《录音知情同意书模板》执行知情同意；模板含"转写数据可用于院内模型优化"的**独立勾选同意**条款（可撤回、先脱敏、不出院） |

## 七、实施路径：从签约到上线

| 阶段 | 内容 | 双方投入 | 产出 |
|---|---|---|---|
| **① 前置对齐** | 确认网络方案（§五）、服务器与环境、入口域名与 HTTPS 方案、试点科室 | 信息科 + 医务科 | 部署环境就绪；同意书模板审定 |
| **② 数据供给打通** | 我院提供 8 表导出/视图（字段字典已给）；先以离线导出表接入，后续谈实时接口 | 信息科 / 病历厂商 | 可用的 HIS 素材通道 |
| **③ 院内安装** | 交付包入场：`install.sh` 一键安装 → 反代配置 → `verify.sh` 自动化验收 | 我方实施 + 信息科复核 | 系统可访问，自动化验收全绿 |
| **④ 试运行与培训** | 使用科室操作培训（录音→生成→四色确认→归档→审签）；信息科运维培训（日志/备份/更新/回滚） | 双方面向 | 培训签认 |
| **⑤ 正式验收** | 逐条走《验收测试报告模板》：自动化项 + 人工项，**不带病验收** | 双方签字 | 《验收测试报告》签署 |
| **⑥ 日常运维（移交信息科）** | 容器健康监控、每日数据库备份、版本更新与回滚、密钥轮换 | 信息科（我方支持） | 运维台账 |

**版本更新与回滚的形态**：更新 = 换新版本镜像包 + 重启 API 容器（静态页面卷挂载，改动即时生效）；回滚 = 切回上一版本代码并重启。**不涉及院内系统的任何改造**，这是容器化交付相对裸机部署的主要优势。

## 八、常见疑问（院方常问）

**Q：一定要 Docker 吗？能不能按院内规范裸机装？**
可以但不在标准交付范围：静态页面用任意 HTTP 服务托管、API 用 `python3 server/llm_api.py` 起进程（systemd 托管）亦可运行。推荐 Docker 的理由是资源限幅、健康检查、自动重启、版本一致性——这些正是医院长期稳定运行所需要的。

**Q：以后想换语言模型厂商 / 语音厂商怎么办？**
配置级切换。语言模型只要兼容 OpenAI 接口，改配置地址与模型名；语音识别在适配器契约下可插拔（云端厂商与本地开源引擎均已留位）。因此院方不会被单一厂商绑定。

**Q：AI 会不会自己乱写病历？**
不会。系统对每个字段标注来源，无素材的病史类字段直接拦截不生成（"宁缺毋造"）；生成的只是草稿，医生确认后才能归档；全过程可溯源到录音原文。

**Q：我们医院的方言很重，能识别准吗？**
山东方言医疗场景我方已做过真实录音实测与专门优化（热词表、方言纠错级联、双引擎交叉校订、可离线运行的自建引擎），并把评测口径与提升路径全部文档化。这一块的投入是长期持续的，实施时会一并说明当前水平与后续提升计划。

**Q：等保测评能过吗？**
部署形态（内网私有化、统一入口、数据不出院、全程审计）符合等保对网络边界与安全审计的通用要求；正式测评由院方统筹，我方提供部署说明、审计留痕、权限设计等配合材料。

## 九、一页速览（汇报用）

> **交付形态**：院内服务器 Docker 私有化部署，医生浏览器访问（B/S），患者数据不出院。
> **交付物**：离线镜像 + 全量代码 + 一键安装/验收脚本 + 配置模板 + 完整文档集 + 培训验收。
> **院方需备**：一台内网服务器（建议 8 核 16G / 200G 盘）、MySQL 库、nginx 入口 + HTTPS、HIS 8 表数据供给、试点科室。
> **唯一关键决策**：AI 能力走白名单云 API（质量优先）还是全本地零外呼（合规优先）——**纯配置差异，切换不动代码**，建议试点期用前者、并行评测后按信息科要求切后者。
> **合规承诺**：数据不出院、四色确认严禁臆造、责任主体是医生、全程审计留痕、交付物零患者数据、录音知情同意。
> **上线路径**：前置对齐 → 数据打通 → 一键安装 → 培训试运行 → 逐条验收签字 → 移交运维。
